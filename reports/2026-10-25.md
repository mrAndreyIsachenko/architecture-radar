## Detailed Reviews

### nasa/openmct

Open MCT informs `satellites-space-systems` through a reusable telemetry-and-time coordination layer rather than through its UI or mission branding. The useful mechanism is the combination of per-view independent time contexts, abortable historical telemetry requests, and strategy-aware subscription caching. The verified flow runs from `TelemetryCollection.load()` through bounded request setup, `TelemetryAPI.standardizeRequestOptions()`, request interception, abort-controller guarded historical fetches, and batched subscription fan-out; `TimeAPI.getContextForView()` and `addIndependentContext()` then keep each view on its own time context while still following the global time system.

- E1 source verified: `src/api/telemetry/TelemetryCollection.js::load`, `_requestHistoricalTelemetry`, `_initiateSubscriptionTelemetry`, and `destroy` manage the historical request, subscription setup, and abort/cleanup lifecycle.
- E1 source verified: `src/api/telemetry/TelemetryAPI.js::standardizeRequestOptions`, `applyRequestInterceptors`, `request`, and `subscribe` normalize request bounds, apply interceptors, issue abortable requests, and cache subscriptions by strategy.
- E1 source verified: `src/api/time/TimeAPI.js::addIndependentContext`, `getContextForView`, `addTimeSystem`, and `addClock` manage per-view time contexts and the time-system registry.
- E2 test verified: `src/api/telemetry/TelemetryAPISpec.js::telemetry batching support` verifies cache-key separation, strategy fan-out, and legacy-provider fallback.
- E2 test verified: `src/api/time/TimeAPISpec.js::Provides a default time context`, `Without a clock, is in fixed time mode`, and `Provided a clock, is in real-time mode` verify the time-context baseline and clock-driven mode switch.

Principal components:

- Telemetry collection object that owns historical load, live subscription setup, bounds filtering, and teardown.
- Telemetry API service that resolves providers, normalizes options, applies interceptors, and multiplexes strategy-specific subscriptions.
- Time API that owns global time systems, clocks, and view-scoped independent contexts.

Most interesting mechanism: the subscription cache is keyed by domain object plus a hash of subscription options, so latest and batch consumers can share a provider subscription without collapsing strategy semantics. That is more disciplined than a naive one-subscriber-per-view model.

Baseline comparison: a simpler mission-control client would keep one global time window and one provider subscription per consumer. Open MCT instead preserves per-view time context and batch/latest strategy semantics while still making the request path abortable.

Reusable:

- Separate global time state from per-view time contexts.
- Cache provider subscriptions by strategy and options hash.
- Put request interception in front of provider execution, not behind it.
- Make historical request teardown abortable and explicit.

Do not copy:

- Do not copy the subscription cache without the strategy contract and test coverage that proves latest and batch behavior remain distinct.
- Do not assume the independent-context pattern is free; it adds state bookkeeping and path comparison logic.

Production-quality signals:

- Source and tests both cover the time-context baseline and the request/subscription contract.
- The telemetry request path has explicit abort and cleanup handling.
- Subscription behavior is guarded by cache-key separation and strategy-aware fan-out.

Experimental or incomplete for our needs:

- The review did not trace a real mission data source through a live deployment, but the contract is already exercised in source and tests.

Hidden costs and failure modes:

- Subscription caching can hide incorrect strategy propagation if the provider contract changes.
- Independent contexts require careful object-path comparisons to avoid stale view state.
- Abortable request handling adds lifecycle complexity that downstream providers must respect.

Adoption experiment:

Attach a custom telemetry provider to Open MCT, create one latest and one batch subscription for the same domain object, and verify that each consumer receives the expected shape while a view-specific time context remains isolated from the global time bounds.

## PaddlePaddle/PaddleOCR

PaddleOCR informs `document-ai-ocr` through a structured document-parsing pipeline rather than a generic OCR wrapper. The reusable mechanism is the poll-backed job client combined with page-level provenance in the parsed result. The verified flow runs from `PaddleOCRClient.parse_document()` or `ocr()` through source validation, payload normalization, asynchronous job submission, backoff polling, result fetch, and typed parsing into `DocParsingResult` or `OCRResult`; the source pipeline in `StructureSystem.__call__()` then combines layout detection, OCR, table recognition, formula recognition, and per-region filtering.

- E1 source verified: `paddleocr/_api_client/client.py::PaddleOCRClient.parse_document`, `ocr`, `submit_document_parsing`, `submit_ocr`, and `_submit` normalize input sources, select the model, and dispatch the job.
- E1 source verified: `paddleocr/_api_client/_poller.py::poll_until_done`, `parse_ocr_result`, and `parse_doc_parsing_result` poll until completion, fetch JSONL, and preserve markdown, exports, input-image references, and raw payloads.
- E1 source verified: `ppstructure/predict_system.py::StructureSystem.__init__`, `__call__`, and `_predict_text` compose layout, text, table, and formula subsystems into the final structure output.
- E2 test verified: `tests/pipelines/test_pp_structurev3.py::test_predict` and `test_predict_params` exercise the PPStructureV3 pipeline and parameter forwarding.
- E2 test verified: `tests/api_client/test_core.py` covers payload key conversion, raw-field preservation, model resolution, and input validation.

Principal components:

- Synchronous client facade over async OCR/document-parsing jobs.
- Poller with bounded backoff and explicit job-state validation.
- Structure pipeline that composes layout, text, table, and formula subsystems.
- Result mappers that preserve raw payloads, exports, images, and page-level metadata.

Most interesting mechanism: the client returns typed page objects with markdown, images, exports, and raw payloads preserved, so the parsing result is not collapsed into a plain text dump. That makes downstream provenance and re-rendering easier.

Baseline comparison: a conventional OCR wrapper would run inference once and return extracted text. PaddleOCR instead wraps a job API, polls until completion, and keeps structured page data with explicit provenance fields.

Reusable:

- Treat asynchronous OCR jobs as typed polling workflows instead of fire-and-forget calls.
- Preserve raw result fragments alongside parsed fields.
- Keep layout-aware filtering separate from the transport/client layer.
- Model selection and request validation should happen before the backend call.

Do not copy:

- Do not copy the synchronous facade without live runtime validation against a representative document batch.
- Do not collapse page-level provenance back into plain text if downstream consumers need markdown, images, or export artifacts.

Production-quality signals:

- Client and parser code are strongly typed and explicit about job state, payload shape, and parse errors.
- The structure pipeline composes multiple document subsystems instead of hard-coding one extraction mode.
- Tests cover parameter forwarding and the basic pipeline path.

Experimental or incomplete for our needs:

- The reviewed evidence still needs a live runtime batch against real OCR/document inputs to validate the backend path, timeout behavior, and mixed-document stability.

Hidden costs and failure modes:

- Polling and backoff introduce runtime latency and timeout sensitivity.
- Multi-stage document parsing can fail at any stage, so result shape stability depends on every backend response staying schema-compatible.
- Layout-aware filtering can hide text if upstream layout detection is wrong.

Adoption experiment:

Run `parse_document()` on a mixed document batch with representative PDF and image inputs, then verify that the returned pages preserve markdown, images, exports, raw payloads, and stable page counts without timeout or parse failure.

## deepseek-ai/deepseek-harness

DeepSeek Harness informs `ai-llm-systems` through a semantic checkpoint barrier before dispatch. The useful mechanism is still the same as the prior review: session state is flushed before model or top-level tool execution, sandbox mode is replayed from durable session state, and the JSONL session store remains the persistence boundary. The current head is a merge commit that expands the `.agents/notes` documentation and related architecture-note scaffolding, but it does not change the core runtime contract that was already reviewed.

- E1 source verified: `packages/session/session-persistence/src/index.ts::flush` and the per-session handle logic make durability the persistence boundary.
- E1 source verified: `packages/session/session-checkpoint-policy/src/index.ts` flushes session state before model dispatch, top-level tool dispatch, and agent pre-step execution, and fail-closes on checkpoint failure.
- E1 source verified: `packages/session/session-persistence-jsonl/src/index.ts` and `packages/session/session-persistence-jsonl/src/storage.ts` register the JSONL backend and enforce the single-writer chain and monotonic reads.
- E1 source verified: `packages/sandbox/sandbox-policy/src/index.ts` and `packages/sandbox/sandbox-policy/src/session-mode.ts` keep sandbox mode as durable session state.
- E2 test verified: `apps/cli/tests/profiles/headless/tests/semantic-checkpoint.expected.e2e.ts` and `packages/session/session-persistence-jsonl/tests/lease.two-process.e2e.ts` verify resumed semantic output and lock takeover.

Principal components:

- CLI dispatcher that boots profiles, plugins, and config dumps.
- Session persistence stack with JSONL generation storage.
- Checkpoint policy that forces flush-before-dispatch.
- Sandbox policy that persists execution posture.

Most interesting mechanism: the runtime turns checkpoint flush into a semantic precondition for dispatch. That is stronger than a best-effort background flush, because a checkpoint failure blocks downstream model or tool execution.

Baseline comparison: a simpler agent runtime would log state asynchronously and let the next dispatch proceed optimistically. DeepSeek Harness instead makes persistence part of the execution contract.

Reusable:

- Put durability barriers directly in tool/model dispatch hooks.
- Treat sandbox mode as durable state, not request-local metadata.
- Use lease-backed single-writer storage for session logs.

Do not copy:

- Do not copy the runtime without a real restart or process-kill validation on the same session ledger.
- Do not assume the JSONL generation layout is a generic storage format.

Production-quality signals:

- The checkpoint barrier is enforced at the semantic boundary where side effects can start.
- The session persistence contract is explicit about contiguity, ownership, and durability.
- The backend validates leases and storage state rather than trusting a best-effort append.

Experimental or incomplete for our needs:

- The reviewed evidence still needs a live process-kill and restart cycle on the same session ledger.

Hidden costs and failure modes:

- Flush-before-dispatch can amplify backend latency into user-visible pauses.
- A stale or lost write lease can make replay and recovery dependent on filesystem behavior.
- Session-mode replay only helps if every side-effecting path routes through the same persistence barrier.

Adoption experiment:

Kill the runtime after a request prefix or top-level tool call has been flushed, restart the same session ledger, and confirm that the same request prefix, sandbox mode, and tool intent reappear without duplicate side effects.
