## Detailed Reviews

### `yaogdu/AgentLedger`

`Runtime.run_once` leases one step, builds an `AgentContext`, appends an `agent_started` event, commits the state patch on success, and turns approval / simulated-crash / retryable failures into explicit step states; `ReplayEngine.replay` walks the stored events and artifacts without calling tools again, while `EvidenceExporter` packages the run into a signed-ish evidence bundle and HTML inspector. The reusable mechanism is an evidence-carrying execution envelope with tool governance and replay-safe dispatch, not the multi-language packaging or dashboard chrome. The baseline is a plain agent loop with opaque side effects and no replay boundary.

What is unusual is the combination of durable state, Tool Ledger semantics, policy gates, replay export, and cross-language runtime baselines in one repository. The production-quality signs are strong tests for crash retry, replay non-execution, high-risk tool denial, schema validation, stale-lease rejection, and inspector / evidence-bundle round-tripping. What remains experimental is the breadth of optional adapters and the lack of a live worker-kill / restart proof on the same ledger.

This informs the `ai-llm-systems` problem set around long-running agents, tool-use governance, replayable evidence, and provenance-carrying execution graphs. Reuse the ledger / policy / replay concepts, not the dashboard or the exact adapter surface. Before adoption, still validate a real process-kill + restart cycle on the same ledger and keep the tool idempotency contract under a live side effect.

### `Sri-Krishna-V/bumblebee`

`Pipeline.stream` sorts documents by size, streams each one through render → layout → crop → OCR in page chunks, closes page images promptly, and emits failure stats instead of raising; `textlayer.py` trusts embedded PDF text only when page-level coverage is high enough, and `runs.py` writes `stats.json` last so resumability can treat it as the completion marker. The reusable mechanism is a resumable OCR pipeline with a text-layer fast path and bounded retry, not the hosted API or Modal wrapper. The baseline is a monolithic PDF OCR job that renders everything first and only then discovers failures.

What is unusual is the combination of chunk streaming, per-page text-layer trust, adaptive retry at 2x DPI, and storage-aware resumability. The production-quality signals are good GPU-free tests for chunking, image cleanup, empty-PDF handling, render failures, OCR failures, and storage refiltering. What remains experimental is the live GPU / model stack, the hardcoded retry budget, and the corpus-specific tuning of confidence thresholds and layout backend choice.

This informs `document-ai-ocr` problems around layout-aware extraction, page/region provenance, failure-preserving batch conversion, and mixed scanned / born-digital handling. Reuse the streaming pipeline shape, the completion-marker contract, and the text-layer trust gate; do not copy the exact model pair or the web / Modal packaging. Before adoption, validate on a real mixed-quality corpus with actual GPU latency and memory pressure.

### `eabz/evm-indexer`

`src/reorg/mod.rs` defines the fork search, purge primitive, and reorg guard; `src/pipeline/backfill.rs` turns module backfill into a read-only scan, a bounded purge of only the changed module rows, an epoch bump, and a chunked reinsert; the tests in `src/reorg/tests.rs` and `src/pipeline/sync_tests.rs` exercise shallow/deep reorgs, start-block floors, hole handling, and restart / failure behavior. The reusable mechanism is a reorg-safe materialization window with purge-and-reinsert repair, not the control panel or chain-specific analytics tables.

What is unusual is the ClickHouse epoch / tombstone repair model: the live indexer never issues DELETE, backfill is idempotent and safe beside the live writer, and the one-process-per-chain assumption is explicit. The production-quality signs are the bounded fork search, the explicit fatal path when reorgs exceed the configured depth, the read-only scan before mutation, and the test matrix for holes and restart behavior. What remains experimental is live HyperSync / ClickHouse operational behavior under real reorg churn and storage pressure.

This informs `blockchain-intelligence` problems around reorg-safe incremental indexing, transaction interpretation, and restartable backfills. Reuse the purge-and-reinsert shape and the epoch floor, not the whole HyperSync / ClickHouse deployment posture. Before adoption, prove the same behavior in a live operational run with actual chain churn.
