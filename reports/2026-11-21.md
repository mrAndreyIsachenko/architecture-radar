## Detailed Reviews

### SuperDeMan/drone-agent

This repository informs `drones-robotics-autonomy`, especially mission planning, command authorization, replay-safe telemetry, and fail-safe recovery. The reusable mechanism is the separation between a human-reviewable `MissionSpec`, a compiled `MissionPackage`, and a guardian that only accepts leased, signed, package-bound intents.

`MissionSpec` rejects control-level keys in task parameters and validates the task DAG before compilation. `compile_spec` expands inspection tasks into framework nodes, fills registry-bound defaults without overwriting authored values, and computes a deterministic package hash. `admit` then checks capability, spatial, time, energy, and parameter binding. `verify_package` rejects unsigned, tampered, expired, wrong-robot, and wrong-key packages before the guardian trusts them. `Guardian` installs leases, rejects stale epochs and replayed heartbeats, binds each intent to a declared phase, and only dispatches when the lease, heartbeat, and package remain coherent.

- E1 source verified: `src/drone_agent/contracts/mission.py::TaskNode`, `_validate_dag`, and `MissionSpec` enforce the planner boundary, control-key filtering, DAG validation, and approved-scope fields.
- E1 source verified: `src/drone_agent/admission/compiler.py::compile_spec` and `lower_inspection` lower the authored spec into a deterministic package without overwriting authored values.
- E1 source verified: `src/drone_agent/admission/admission.py` applies capability, scope, and parameter binding checks before a package is accepted.
- E1 source verified: `src/drone_agent/runtime/signing.py::verify_package` and `src/drone_agent/guardian/core.py::install_lease`, `heartbeat`, and `submit` gate command execution on signature, lease, replay, and phase checks.
- E2 test verified: `tests/admission/test_compiler_and_admission.py`, `tests/contracts/test_package_signatures.py`, `tests/runtime/test_uplink.py`, and `tests/runtime/test_safety_runtime.py` cover package binding, signature rejection, rollback protection, accepted-package forwarding, and restart-safe guardian replay.

The interesting mechanism is the approval hash plus lease epoch fence. The package hash binds the compiled mission to the human approval, while the lease and heartbeat logic keep the guardian from accepting stale or replayed work. That is stronger than a simple command queue because it treats the mission envelope itself as a security and recovery boundary.

Production-quality signals are strong source contracts, explicit replay tests, and a broad safety-oriented runtime surface. The main gap is that the repository still needs operational validation beyond SITL and simulated adapters, especially if the package/guardian boundary is to be trusted on real aircraft or field hardware.

Use the package boundary, lease-fenced submission path, and restart-aware journals as reusable concepts. Do not copy the full flight stack or assume the current test matrix substitutes for an operational hardware run. Before adoption, I would still want a real flight-controller or HIL validation that exercises the same package/lease/replay path under restart and recovery churn.

### OpenBMB/MiniCPM-OCR

This repository informs `document-ai-ocr`, especially layout-aware extraction, page and region provenance, streaming document parsing, and partial-success recovery. The reusable mechanism is a staged OCR pipeline that separates backend validation, layout detection, recognition, and assembly into explicit phases.

`validate_engine_config` rejects unsupported backend types and incomplete connection data. `create_backend` builds a backend client only after config validation. `parse_layout_run`, `prepare_run`, `infer_run`, and `pipelined_run` split layout detection from recognition, write per-page and per-block runtime records, preserve page order, and keep partial page failures from aborting the whole run. `assemble_document_json` and `assemble_documents_json` preserve input order and report partial or failed documents instead of collapsing everything into a single binary success/failure result.

- E1 source verified: `sdk/minicpmvocr/backends/__init__.py::validate_engine_config` and `create_backend` enforce explicit engine configuration and backend selection.
- E1 source verified: `sdk/minicpmvocr/backends/client.py::VLMClient` handles multiple endpoints, readiness checks, retry-on-overflow behavior, streaming deltas, and per-request latency metrics.
- E1 source verified: `sdk/minicpmvocr/pipeline/staged.py::parse_layout_run`, `prepare_run`, and `infer_run` define the staged parse path and its runtime records.
- E1 source verified: `sdk/minicpmvocr/pipeline/overlapped.py::pipelined_run` executes layout and OCR work concurrently while preserving page completion ordering and failure isolation.
- E2 test verified: `sdk/tests/test_layout_parallelism.py`, `sdk/tests/test_multi_input.py`, and `sdk/tests/test_stream_pages.py` cover deterministic page order, layout worker scaling, partial-success document JSON, and streamed page delivery.

The most interesting mechanism is the layout-first, overlap-aware pipeline. Layout is detected first, recognition is dispatched only for the resulting blocks, and the assembly layer keeps page ordering and partial failures visible. That is useful because it preserves structure while still allowing concurrency and mixed success.

The repo looks production-oriented at the orchestration layer, but it still depends on live backends and workload-specific validation. The remaining gap is a real mixed-corpus backend run that proves the retry, streaming, and partial-success behavior under realistic server latency and model failures.

Reuse the staged layout/recognition split, the explicit backend validation, and the ordered partial-success assembly. Do not copy the entire backend matrix blindly or treat optional outputs as if they were canonical input. Before adoption, I would still require a live backend run on a mixed corpus to confirm the runtime characteristics under real latency.
